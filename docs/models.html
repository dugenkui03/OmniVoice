OmniVoice Engineering Notes

从工程文件看懂 OmniVoice 的 models 组成

这篇文章不是论文解读，而是站在工程项目的角度，解释 OmniVoice 里“模型”到底由哪些文件、目录和运行部件组成，以及它们在推理、训练、评估时分别负责什么。

模型资产目录：.models/OmniVoice

本地 .models/OmniVoice 是 Hugging Face 模型仓库的一个快照。它不是源码包，而是运行推理时真正要加载的“模型资产包”。

文件或目录 含义 在工程里的作用
model.safetensors OmniVoice 主模型权重，当前本地约 2.3GB。 由 OmniVoice.from_pretrained(...) 加载，包含 LLM 主干、音频 embedding、音频预测头等参数。
config.json 模型结构配置。 声明 model_type=omnivoice、8 个音频 codebook、音频词表大小 1025、mask token id 1024，以及内部 LLM 是 Qwen3 风格配置。
tokenizer.json 文本 tokenizer 的主体文件。 把文本、语言标记、风格指令、特殊 token 转成文本 token id。
tokenizer_config.json 文本 tokenizer 的加载配置。 告诉 Transformers 如何恢复 tokenizer 行为。
chat_template.jinja 聊天模板文件。 继承自底层文本模型生态，OmniVoice 主流程里更重要的是自定义的语言、指令和文本边界 token。
audio_tokenizer/ HiggsAudioV2TokenizerModel 的独立资产目录。 负责把波形压缩成离散音频 token，也负责把生成出的音频 token 解码回波形。

这里有一个容易混淆的点：OmniVoice 主模型不是直接输出 WAV 波形，而是先输出离散的音频 token；真正把 token 变回声音的是 audio_tokenizer。

资产文件里的子模块，是不是被合并成一个权重了？

可以把当前模型资产理解成“两包权重 + 若干配置文件”。第一包是 OmniVoice 主模型的 model.safetensors，第二包是 audio_tokenizer/model.safetensors。它们共同完成 TTS，但并没有全部揉成一个单独文件。

flowchart LR A["Qwen/Qwen3-0.6B 初始化来源"] --> B["OmniVoice 主模型训练"] C["新增音频层: audio_embeddings / audio_heads"] --> B B --> D[".models/OmniVoice/model.safetensors"] E["HiggsAudioV2TokenizerModel"] --> F[".models/OmniVoice/audio_tokenizer/model.safetensors"] D --> G["推理时加载 OmniVoice 主模型"] F --> H["推理时加载 audio tokenizer"] G --> I["生成音频 token"] H --> J["音频 token 和 WAV 互转"]
资产文件 里面看到的主要子模块 来源/角色 是否是合并文件
.models/OmniVoice/model.safetensors llm.*、audio_embeddings.weight、audio_heads.weight、codebook_layer_offsets llm.* 是 Qwen3ForCausalLM 风格主干；音频 embedding 和 audio heads 是 OmniVoice 为语音 token 任务增加的层。 是 OmniVoice 主模型的一个 state_dict 文件。它把主模型内部各层参数保存在同一个 safetensors 文件里，但不包含独立的 audio tokenizer 权重。
.models/OmniVoice/audio_tokenizer/model.safetensors semantic_model.*、acoustic_encoder.*、acoustic_decoder.*、quantizer.* 这是 HiggsAudioV2TokenizerModel，内部又包含语义模型、声学编码器/解码器和量化器，负责 WAV 和音频 token 之间互转。 是另一个独立模型的权重文件。推理时由 HiggsAudioV2TokenizerModel.from_pretrained(...) 单独加载。
config.json 与 audio_tokenizer/config.json 模型结构、层数、hidden size、codebook 数量、采样率等元信息。 告诉 Transformers 应该按什么类和结构把权重恢复成可运行模型。 不是权重，只是“装配说明书”。没有这些配置，单独的 safetensors 很难正确还原为模型对象。

所以，“合并”这件事要分两层理解：在主模型内部，Qwen 主干参数和 OmniVoice 新增的音频层参数确实一起保存进了主 model.safetensors；但从完整 TTS 系统看，audio tokenizer 仍然是单独的模型资产目录，并没有被合进主模型权重文件。

更准确的说法是：训练/保存时，Transformers 的 save_pretrained 体系会把一个模型对象的参数字典保存成 safetensors 权重文件；这不是简单文件拼接，而是按模块名保存参数张量。加载时再根据配置和 key 名称把这些张量放回对应子模块。

主模型代码：omnivoice/models/omnivoice.py

这个文件是 models 主题的核心。它既定义了模型结构，也定义了推理流程。可以把它理解成 Java 里的一个核心 service + model class，但它继承的是 Hugging Face 的 PreTrainedModel。

关键类

类名 职责
OmniVoiceConfig 描述模型结构。比如音频词表大小、mask id、codebook 数量、音频 codebook loss 权重，以及内部 LLM 的配置。
OmniVoice 主模型类。里面有底层 LLM、音频 embedding、音频预测头、推理生成、参考音频处理、后处理等逻辑。
OmniVoiceGenerationConfig 推理参数集合。比如生成步数 num_step、guidance、温度、长文本切块阈值、是否后处理等。
VoiceClonePrompt 语音克隆提示对象。缓存参考音频 token、参考文本、参考音量 RMS，便于重复生成。
GenerationTask 把一次生成请求规范化成 batch 任务，包含文本、目标音频长度、语言、风格指令和参考音频 token。

模型内部怎么“接上”音频

OmniVoice 内部有三块最关键的神经网络部件：

self.llm

底层语言模型主干。当前配置显示是 Qwen3/Qwen3ForCausalLM 风格，hidden size 为 1024，28 层，16 个 attention heads。

audio_embeddings

把 8 个音频 codebook 的 token id 映射成 LLM hidden size 维度的 embedding。

audio_heads

把 LLM hidden states 投影回音频 token 概率，形状可以理解成 8 个 codebook 分别预测 1025 个类别。

文本 token / 风格 token / 参考音频 token / 待生成的 mask token
        ↓
_prepare_embed_inputs 把文本 token 和音频 token 转成统一 hidden 表示
        ↓
self.llm 处理整段上下文
        ↓
audio_heads 输出每个 audio codebook 的 token logits
        ↓
迭代解 mask，得到完整音频 token
        ↓
audio_tokenizer.decode 还原 WAV 波形

Qwen 不是文本模型吗，为什么能做语音？

这里的关键点是：OmniVoice 不是拿一个原封不动的 Qwen 聊天模型直接“说话”。它复用了 Qwen3 这一类模型的 Transformer 主干能力，再把输入和输出接口改造成适合语音 token 的形式。

flowchart LR A["普通 Qwen 文本模型"] --> B["文本 token embedding"] B --> C["Qwen Transformer 主干"] C --> D["文本 lm_head"] D --> E["下一个文本 token"] F["OmniVoice"] --> G["文本 token + 音频 token embedding"] G --> H["Qwen Transformer 主干"] H --> I["OmniVoice audio_heads"] I --> J["8 路音频 codebook token"] J --> K["audio_tokenizer.decode"] K --> L["WAV 语音"]
概念 在普通 Qwen 里 在 OmniVoice 里
主干模型 Transformer 层负责建模 token 序列关系。 仍然负责建模序列关系，只是序列里混合了文本 token、语言/风格 token、参考音频 token 和待预测音频 token。
输入 embedding 文本 token id 进入文本 embedding。 文本 token 走原文本 embedding；音频 token 走 audio_embeddings，再统一喂给同一个 Transformer。
输出头 lm_head 预测下一个文本 token。 audio_heads 预测音频 codebook token。也就是说，输出目标已经从“文字”换成了“离散音频 token”。
最终产物 一串文本 token，解码后得到文字。 一串音频 token，经 audio_tokenizer.decode 后得到语音波形。

所以，“主干 LLM 是 Qwen3ForCausalLM 架构”更准确地理解为：OmniVoice 借用了 Qwen3 这一代文本大模型成熟的 Transformer 结构和初始化权重，让它不再只预测文字，而是在新的音频 embedding、音频预测头和语音训练目标下学习预测音频 token。

训练配置里的 llm_name_or_path: "Qwen/Qwen3-0.6B" 表示：如果不是从已经训练好的 OmniVoice checkpoint 初始化，就先从 Qwen3-0.6B 拿到一个会处理长序列、会建模语言上下文的基础 Transformer。随后，OmniVoice 会增加音频相关层，并通过语音数据训练，让这个主干适应“文本条件下生成音频 token”的任务。

用“输入、处理、输出”理解 Qwen3 Transformer 主干

可以用一种很工程化、接近冯诺伊曼机器的方式理解 Qwen3 Transformer 主干：它本身不是“文字打印机”，而是一个序列计算器。只要输入被表示成同一维度的向量序列，它就负责在这些位置之间做上下文计算，最后输出每个位置的上下文向量。

阶段 在 OmniVoice 里的具体含义 工程文件对应点
输入 一串 hidden 向量，不是原始文字，也不是原始 WAV。文本 token 先经过文本 embedding；音频 token 先经过 audio_embeddings；两者被整理成同一种 hidden size 的序列。 _prepare_embed_inputs 把 input_ids 和 audio_mask 变成 inputs_embeds。
处理 Transformer 层反复做 attention 和前馈网络计算。attention 让每个位置读取其他位置的信息，例如目标音频 mask 位置可以参考文本、语言、风格、参考音频 token。 self.llm(inputs_embeds=..., attention_mask=...)。
输出 每个序列位置对应一个 hidden state。这个 hidden state 本身还不是文字或语音，它只是“上下文计算后的中间表示”。接什么输出头，才决定它被解释成文字概率还是音频 token 概率。 hidden_states = llm_outputs[0]，然后交给 audio_heads。
flowchart LR A["输入: token id + audio_mask"] --> B["_prepare_embed_inputs"] B --> C["统一 hidden 向量序列"] C --> D["Qwen3 Transformer 主干"] D --> E["上下文 hidden states"] E --> F["audio_heads"] F --> G["音频 token 概率"]

类比一下：Qwen 主干像一个很强的“序列理解和生成发动机”；普通文本模型给它接的是文字输出头，OmniVoice 给它接的是音频 token 输出头。发动机相似，但输入输出接口和训练目标已经变了。

推理流程：generate 做了什么

README 里示例调用的是 model.generate(...)。这个方法支持三种模式：语音克隆、语音设计和自动音色。它们最后都会走到同一个音频 token 生成器。

flowchart TD A["用户调用 model.generate"] --> B["整理输入: 文本 / 语言 / instruct / ref_audio"] B --> C{"是否有参考音频"} C -->|有| D["create_voice_clone_prompt: 波形转音频 token"] C -->|无| E["使用 voice design 或 auto voice"] D --> F["估算目标音频 token 长度"] E --> F F --> G{"是否超过长文本阈值"} G -->|否| H["_generate_iterative 直接生成"] G -->|是| I["_generate_chunked 分块生成"] H --> J["audio_tokenizer.decode"] I --> J J --> K["去静音 / 音量调整 / fade 和 padding"] K --> L["返回 numpy 音频数组"]

用“输入、处理、输出”理解整个推理过程

如果把一次 TTS 推理看成一台冯诺伊曼式机器，它的输入不是只有一句文字，而是一组条件；处理过程不是一步生成 WAV，而是先把条件转成 token 序列、再迭代填空；输出也分为中间输出和最终输出。

阶段 数据是什么 模型/代码做什么 产物是什么
输入 目标文本、语言 ID、voice design 指令、可选参考音频和参考文本、生成参数。 generate 接收参数，_preprocess_all 统一整理 batch、语言、指令、速度和目标长度。 GenerationTask：一份标准化后的生成任务。
条件编码 参考音频还是 WAV 波形，文本还是字符串。 create_voice_clone_prompt 用 audio tokenizer 把参考音频转成音频 token；文本 tokenizer 把文本、语言、指令转成文本 token。 文本 token、风格 token、参考音频 token。
构造待求解区域 目标语音还不存在，只知道估算长度。 _prepare_inference_inputs 创建一段全是 audio_mask_id 的目标音频 token 区域。 “条件 token + 待填空音频 mask token”的完整序列。
核心计算 完整 token 序列和 attention mask。 _generate_iterative 多轮调用 self(...)，由 Qwen3 Transformer 主干计算 hidden states，再由 audio_heads 给出音频 token 概率。 每一轮填入一部分更有把握的音频 token。
中间输出 8 路 codebook 的离散音频 token。 如果是长文本，_generate_chunked 会分块生成，再把多个 chunk 交给后续解码。 完整或分块的音频 token 序列。
最终输出 音频 token 还不是人耳能听的声音。 _decode_and_post_process 调用 audio_tokenizer.decode 转成波形，并做去静音、音量调整、淡入淡出和 padding。 可保存为 WAV 的 numpy 音频数组。
flowchart TD A["输入: 文本/语言/指令/参考音频/生成参数"] --> B["预处理: 标准化为 GenerationTask"] B --> C["编码: 文本 token + 音频 token"] C --> D["构造: 待生成区域填 audio_mask_id"] D --> E["计算: Transformer 主干 + audio_heads"] E --> F["迭代: 逐步把 mask 替换成音频 token"] F --> G["解码: audio_tokenizer.decode"] G --> H["输出: WAV 波形数组"]

三种生成模式

模式 用户提供什么 模型内部发生什么
Voice cloning ref_audio，可选 ref_text 参考音频被 audio_tokenizer.encode 变成音频 token；如果没有参考文本，可加载 Whisper ASR 自动转写。
Voice design instruct，例如 male, british accent 指令被规范化后包进 <|instruct_start|> 和 <|instruct_end|>。
Auto voice 只有 text 语言和指令都可以为空，让模型自己选择音色。

音频 tokenizer：不是辅助文件，而是第二个关键模型

.models/OmniVoice/audio_tokenizer 里保存的是 HiggsAudioV2TokenizerModel。它在工程中的地位很高，因为 OmniVoice 主模型学习和生成的对象都是“音频 token”，不是原始波形。

编码阶段

参考音频或训练音频先被编码成多 codebook 离散 token。训练数据里保存的 audio_tokens 就来自这一步。

解码阶段

主模型生成 8 路音频 token 后，再由 audio tokenizer 解码成采样率 24kHz 的音频。

从本地配置看，audio tokenizer 的 sample_rate 是 24000，hop_length 是 960，主模型使用 num_audio_codebook=8。这解释了为什么代码里到处可以看到 (C, T) 这样的音频 token 形状，其中 C 通常就是 8。

训练相关文件如何围绕 models 工作

训练不是另起炉灶，而是复用同一个 OmniVoice 类。差别在于训练时会调用 forward 计算 loss，推理时会调用 generate 逐步生成音频 token。

文件 含义
omnivoice/training/config.py 训练配置 dataclass。记录底层 LLM、音频词表、codebook 数量、batch tokens、学习率、混合精度、checkpoint 等。
omnivoice/training/builder.py 训练装配器。负责加载 tokenizer、创建或加载 OmniVoice、补齐特殊 token，并构建 dataloader。
omnivoice/data/processor.py 把样本加工成模型输入。它会拼接语言、指令、文本 token 和音频 token，并随机 mask 部分音频 token 作为训练目标。
omnivoice/data/collator.py 把多个样本合成 batch。支持 padding 方式，也支持 flex attention 场景下的 sequence packing。
examples/config/*.json 示例训练配置。比如 train_config_finetune.json 从 k2-fsa/OmniVoice 初始化权重，适合微调。
flowchart LR A["JSONL 原始数据"] --> B["extract_audio_tokens"] B --> C["WebDataset shards + labels"] C --> D["OmniVoiceSampleProcessor"] D --> E["DataCollator"] E --> F["OmniVoice.forward"] F --> G["audio_heads logits"] G --> H["masked audio token loss"]

评估模型：eval/models 不是主模型

omnivoice/eval/models 下面的模型容易被误认为 OmniVoice 主体的一部分，但它们主要服务于评估。

路径 用途
omnivoice/eval/models/ecapa_tdnn_wavlm.py 说话人相似度评估相关模型，配合 eval/speaker_similarity/sim.py 使用。
omnivoice/eval/models/utmos.py UTMOS 自然度评分模型结构，配合 eval/mos/utmos.py 使用。
omnivoice/eval/wer/*.py WER/CER 评估脚本，调用不同 ASR 模型转写生成语音，再和目标文本比较。

换句话说，omnivoice/models 是“生产声音”的模型；omnivoice/eval/models 是“评价声音”的模型。

一句话总结

OmniVoice 的 models 不是一个单独文件，而是一套组合：OmniVoice 主模型负责根据文本、语言、风格和参考音频预测离散音频 token；audio_tokenizer 负责音频和 token 之间互转；训练、CLI、Demo、评估模块则围绕这两个核心模型组织工程流程。

参考当前仓库文件：omnivoice/models/omnivoice.py、.models/OmniVoice/config.json、.models/OmniVoice/audio_tokenizer/config.json、omnivoice/training/builder.py、omnivoice/data/processor.py、README.md。
