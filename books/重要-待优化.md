# 重要：待优化

## 1. 推理阶段支持 ReMask 自纠错

### 当前问题

OmniVoice 当前采用单向迭代补全：每轮选择高置信度位置填入 audio token，已经填入的位置随后被排除，不会再次修改。

```text
全 MASK → 填入高置信度 token → 只补剩余 MASK → 完成
```

这种方式实现简单，但早期生成错误会被当作后续输入，存在错误传播风险。模型置信度高也不等于 token 一定正确。

### 优化思路

每轮 `forward()` 后重新评估目标区域，包括已经生成的 token；把部分低置信度 token 重新设为 `audio_mask_id`，在后续轮次重新预测。

```text
MASK → 生成 token → 重新评估置信度
                   ├─ 高置信度：保留
                   └─ 低置信度：重新 MASK → 再生成
```

核心目标是让早期决策可以被修正，而不是一旦填入就永久固定。ReMask 应限制在 target 区域，并通过每轮比例、置信度阈值和最大重试次数避免反复震荡。

### 实现与验证重点

- 修改位置：`OmniVoice._generate_iterative()` 的位置选择与 token 回写阶段。
- 需要确认当前随机 MASK 训练目标是否足以支持推理期 ReMask；必要时增加与新采样过程匹配的训练。
- 对比无 ReMask 与 ReMask 的 WER/CER、说话人相似度、音质、生成稳定性和 RTF。
- 重点观察错字、漏字、重复、局部噪声、音色漂移以及推理耗时。

### 参考方案

[Mask, Sample, Revise: A Revisable CTMC Inference Stack for Guided Discrete Flow Matching Text-to-Speech](https://arxiv.org/abs/2606.13989) 提出的 `SC-ReMask` 允许生成 token 再次转为 MASK，从而修正早期决策。

截至 2026-07-26，尚未找到该论文公开的官方 Hugging Face 模型权重或 Space，现阶段主要作为算法设计参考。

## 2. 用训练数据学习文本对应的音频时长

### 当前问题

当前 `RuleDurationEstimator` 主要根据字符数量和人工权重估算目标音频长度，对语言、标点、停顿和实际语速的刻画有限，容易出现明显偏差。

### 优化思路

复用 OmniVoice 的原始 TTS 训练数据，通过相同的音频预处理和 `audio_tokenizer.encode()` 为每条样本制作目标帧数标签：

```text
真实音频 → audio_tokenizer.encode() → T_frames
文本及控制条件 → 时长预测模型 → 预测 T_frames 或时长范围
```

`audio_tokenizer` 只在离线数据处理阶段生成标签，线上时长预测不需要运行它。预测模型可以输出单个帧数，也可以使用分位数回归输出较短、中位和较长时长，例如 `[P10, P50, P90]`。

### 模型规模

Higgs Audio V2 Tokenizer 需要同时完成波形编码和解码，约有 201.4M 参数；文本时长预测只是一个轻量回归任务，不需要使用同等规模的模型。

- 极简字符模型：约 1M～5M 参数。
- 小型 BiLSTM 或 Transformer：约 5M～20M 参数。
- 第一版建议从约 10M 参数开始，避免直接引入 100M 以上的预训练文本模型。

### 输入与验证重点

- 第一阶段使用 30万～50万条影视剧台词训练并验证，再根据分场景指标决定是否扩大数据量。
- 基础输入：规范化后的文本、语言和标点信息。
- 可选条件：说话人、情绪或风格、语速等会影响真实时长的因素。
- 训练集、验证集和测试集应按剧集划分，不要随机拆分台词，避免同一剧集的数据泄漏。
- 如果只有文本输入，优先预测 `[P10, P50, P90]` 时长范围，因为演员表演造成的时长差异无法仅靠文本完全确定。
- 训练标签应使用与 OmniVoice 推理一致的采样率、裁剪规则、`hop_length` 和 Audio Tokenizer。
- 评测帧数 MAE、相对误差、时长区间覆盖率，并按语言、文本长度和标点类型分别统计。

### 训练数据来源规则

- 优先使用真人影视台词、真实配音成片或录音棚数据，使标签反映真实说话节奏。
- 不应把当前 OmniVoice 依据字符规则确定长度的生成音频作为主要训练数据，否则模型只会重新学习需要替换的字符估算规则。
- 可以使用 IndexTTS 等其他 TTS 模型的默认生成结果制作第一版数据，但不能强制指定 `duration`，避免再次引入人为时长规则。
- 合成数据需要覆盖不同说话人、语言、情绪、风格、语速和标点，并过滤漏读、重复、异常停顿等 bad case。
- 推荐使用合成数据预训练，再用真人影视数据微调；仅使用 IndexTTS 数据时，模型预测的是 IndexTTS 的时长分布，不等同于真实演员的表演时长。

参考模型：[Higgs Audio V2 Tokenizer](https://huggingface.co/eustlb/higgs-audio-v2-tokenizer)。

## 3. 随机采样时使用所选 token 的对应置信度

### 当前问题

`OmniVoice._predict_tokens_with_scoring()` 当前始终使用每个位置的最高 log 概率作为 `confidence_scores`：

```python
confidence_scores = log_probs.max(dim=-1)[0]
```

当 `class_temperature=0` 时，`pred_tokens` 由 `argmax()` 得到，所选 token 与最高分完全对应。开启 `class_temperature` 后，`pred_tokens` 经过 Top-K 和 Gumbel 随机采样，可能不是原始分数最高的 token；此时 `confidence_scores` 仍属于最高分候选，而不一定属于实际选中的 token。

这种不对应可能使某个低概率采样结果获得较高的位置置信度，并在迭代补全过程中被过早固定。

### 优化思路

开启随机采样时，根据 `pred_tokens` 从 `log_probs` 中取出所选 token 的对应分数：

```python
confidence_scores = log_probs.gather(
    dim=-1,
    index=pred_tokens.unsqueeze(-1),
).squeeze(-1)
```

默认贪心模式可以保持现有行为，因为最高分与所选 token 本来就是同一个候选。需要对比“位置最高候选分数”和“实际采样 token 分数”两种排序方式对 WER/CER、音质、随机性和生成稳定性的影响，并与 ReMask 自纠错方案联合评估。

## 4. 根据原台词左右声道响度比例恢复静态声像

### 当前问题

OmniVoice 当前生成单声道语音。直接复制到左右声道会使角色始终位于声场中央；分别对左右声道执行两次 TTS，则可能产生语速、停顿、发音和时长不一致。

### 优化思路

每条角色台词只执行一次 TTS，再根据原台词左右声道的线性 RMS 恢复左右响度比例：

```text
原台词左右 RMS：<L, R>
平均 RMS：M = (L + R) / 2

TTS 单声道先归一到 M
左声道：tts × L / M
右声道：tts × R / M
```

例如原台词左右 RMS 为 `<1, 2>`，平均值为 `1.5`。将 TTS 结果复制成 `<1.5, 1.5>` 后，分别乘以 `<1 / 1.5, 2 / 1.5>`，可得到近似 `<1, 2>` 的左右声道响度。

这种方式能够保留角色偏左或偏右的**静态声像**，同时保证两个声道中的台词内容、停顿和时长完全一致。

### 实现与验证重点

- 应使用线性 RMS；如果输入是 dBFS 或 LUFS，需要先换算成线性增益，不能直接相乘。
- 原音频含有背景音乐或音效时，应优先从对白 stem 或语音有效区间计算左右 RMS，避免环境声干扰角色定位。
- 放大单侧声道后需要检查峰值并使用限幅或整体归一化，避免削波。
- 该方案只能恢复左右响度比例，不能还原双耳时间差、相位、房间反射、前后距离或移动轨迹，因此不等同于完整的空间音频。
